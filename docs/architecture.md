# معماری Loghmeh

Loghmeh از ابتدا به شکل «هسته فروشگاه + افزونه‌ها» ساخته شده است. یعنی افزودن سرویس بعدی نباید باعث دست‌کاری مسیر پرداخت یا سفارش‌های سرویس‌های قبلی شود.

```text
Telegram bot ────────┐
                     ├─> Order core ─> PostgreSQL (source of truth)
Admin dashboard ─────┘          │
                                ├─> PaymentProvider: Aban / future crypto
                                └─> FulfillmentProvider: manual / signed external connector
```

## ماژول‌ها

- `telegram`: گفت‌وگوی ساده کاربر، انتخاب سرویس، گرفتن نام کاربری مقصد و ارسال لینک پرداخت.
- `db`: تنها محل دسترسی به PostgreSQL و اجرای migrationها.
- `payment`: قرارداد پرداخت. اکنون آبان گیت‌وی را پیاده می‌کند؛ کریپتو بعداً فقط به‌صورت یک پیاده‌سازی جدید اضافه می‌شود.
- `fulfillment`: صف تحویل. حالت پیش‌فرض `manual` است تا هیچ خریدی بدون اتصال تأییدشده و آزمایش‌شده اجرا نشود.
- `web`: وب‌هوکِ امضاشده پرداخت، health check و API پنل مدیریت.
- `admin`: صفحهٔ کوچک مدیریت؛ برای راه‌اندازی و پایش اولیه. هر عملیات مهم در `admin_audit_logs` قابل ثبت است.

## وضعیت سفارش

`payment_creating → awaiting_payment → paid → fulfillment_processing → fulfilled`

در هر خطای مبهم مسیر به `requires_review` می‌رود، نه تکرار خودکار پرداخت یا تحویل. این قاعده جلوی تحویل یا شارژ دو‌باره را می‌گیرد.

## قرارداد افزونهٔ تحویل

یک اتصال تحویل خودکار باید بیرون از Loghmeh و با یک کلید HMAC جدا اجرا شود. درخواست، فقط شناسه سفارش، سرویس و نام کاربری مقصد را می‌برد؛ هیچ عبارت بازیابی کیف‌پول، کوکی مرورگر یا رمز حسابی در این پروژه ذخیره نمی‌شود.
